# Урок 2. `useEffect` — побочные эффекты

Страница: `/lesson/2`. Код: `app/routes/lesson-2-use-effect.tsx`.

## Назначение

Рендер должен быть чистым: функция компонента только вычисляет JSX. Но приложению
нужно взаимодействовать с внешним миром: запускать таймеры, делать запросы,
подписываться на события браузера, работать с DOM напрямую. Такие действия
называются **побочными эффектами**.

`useEffect` позволяет выполнить код **после** того, как React применил изменения к
DOM, и описать, как этот код **отменить**. Официальная формулировка: эффект
**синхронизирует** компонент с внешней системой.

## Сигнатура

```ts
useEffect(setup: () => (void | (() => void)), dependencies?: unknown[])
```

| Часть          | Что это |
|----------------|---------|
| `setup`        | функция эффекта. Может вернуть **функцию очистки** (cleanup). |
| cleanup        | функция, которая отменяет то, что сделал `setup`: останавливает таймер, отписывается, отменяет запрос. |
| `dependencies` | массив значений из тела компонента, которые использует эффект. Определяет, когда эффект перезапускается. |

`useEffect` ничего не возвращает.

## Когда выполняется эффект

| Массив зависимостей  | Когда выполняется `setup`                                    | Когда выполняется cleanup                     |
|----------------------|--------------------------------------------------------------|-----------------------------------------------|
| не указан            | после **каждого** рендера                                    | перед каждым следующим запуском и при размонтировании |
| `[]`                 | один раз, после монтирования                                 | при размонтировании                           |
| `[a, b]`             | после монтирования и после рендеров, где изменилось `a` или `b` | перед следующим запуском и при размонтировании |

Зависимости сравниваются с предыдущим рендером через `Object.is`, так же как
состояние в `useState`: примитивы по значению, объекты и функции по ссылке.

## Жизненный цикл по шагам

На примере эффекта D (автоопрос) из урока:

```tsx
useEffect(() => {
  if (!isPolling || !isTabVisible) return
  const id = setInterval(tick, period)
  return () => clearInterval(id)
}, [isPolling, period, isTabVisible, log])
```

1. **Монтирование.** Рендер → коммит (DOM обновлён, браузер отрисовал страницу) →
   `setup`. `isPolling = false`, эффект сразу выходит, cleanup нет.
2. **Пользователь включил автоопрос.** `setIsPolling(true)` → рендер → коммит.
   React сравнивает зависимости: `isPolling` изменилось → запускает `setup`.
   Создаётся таймер, возвращается cleanup №1.
3. **Пользователь ввёл комментарий или пришло новое напряжение.** Рендер → коммит.
   Зависимости не изменились → эффект **не перезапускается**, таймер продолжает
   работать.
4. **Пользователь сменил период.** Рендер → коммит. `period` изменился → React
   **сначала вызывает cleanup №1** (старый таймер остановлен), **потом новый
   `setup`** с новым `period` (новый таймер) → cleanup №2.
5. **Пользователь ушёл со страницы.** Компонент размонтируется → cleanup №2.

Важно: каждый запуск эффекта видит значения **своего** рендера. Cleanup №1 закрывает
именно тот таймер, который создал `setup` №1. Поэтому переменная `controller` в
эффекте D объявлена внутри эффекта: у каждого запуска своя.

## Эффекты урока

| Эффект | Зависимости | Что показывает |
|--------|-------------|----------------|
| A | `[log]` (функция стабильна, по сути `[]`) | монтирование и размонтирование, двойной запуск в StrictMode |
| B | `[voltage, log]` | запуск только при изменении конкретного значения |
| C | `[log]` | подписка на событие браузера (`visibilitychange`) и отписка в cleanup |
| D | `[isPolling, period, isTabVisible, log]` | таймер, отмена запроса, перезапуск при смене зависимостей |
| E | нет массива | выполнение после каждого рендера (пишет только в консоль) |
| `Clock` | `[onLog]` | очистка при размонтировании дочернего компонента |

Эффекты C и D работают вместе: C меняет состояние `isTabVisible`, а оно стоит в
зависимостях D. Когда вкладка скрыта, автоопрос останавливается, чтобы не нагружать
устройство впустую.

## Функция очистки

Правило: **всё, что эффект запустил, cleanup должен остановить**.

| В `setup`                          | В cleanup                              |
|------------------------------------|----------------------------------------|
| `setInterval` / `setTimeout`       | `clearInterval` / `clearTimeout`       |
| `addEventListener`                 | `removeEventListener` с той же функцией|
| `fetch(..., { signal })`           | `controller.abort()`                   |
| открыть WebSocket / подписку       | закрыть соединение / отписаться        |

Без очистки появляются утечки: таймер компонента, которого уже нет на странице,
продолжает отправлять запросы, а при каждом перезапуске эффекта добавляется ещё один
таймер.

## StrictMode: почему эффект выполняется дважды

В режиме разработки React при монтировании выполняет `setup → cleanup → setup`.
Так он проверяет, что после очистки и повторного запуска компонент работает так же,
как после одного запуска. Если очистка написана правильно, пользователь разницы не
заметит. Если неправильно (например, нет `clearInterval`), сразу появится второй
таймер, и ошибка будет видна.

В журнале урока при открытии страницы видно (на странице новые записи сверху,
здесь — в порядке по времени):

```
Clock: монтирование → setInterval
A: монтирование (deps = [])
C: подписка на visibilitychange
Clock: cleanup → clearInterval          ┐
A: cleanup (размонтирование …)          │ проверка StrictMode
C: отписка от visibilitychange          ┘
Clock: монтирование → setInterval
A: монтирование (deps = [])
C: подписка на visibilitychange
```

Эффекты дочернего компонента (`Clock`) выполняются раньше эффектов родителя: React
обходит дерево снизу вверх. Эффекты B и D при монтировании ничего не пишут: у них
сразу срабатывает условие выхода (`voltage === null`, `!isPolling`).

**Не боритесь с этим** флагами вроде «уже запускалось». Двойной запуск есть только
в режиме разработки, и это проверка вашей функции очистки.

## Запросы данных в эффекте

Функцию `setup` нельзя объявить как `async`: асинхронная функция возвращает
`Promise`, а React ждёт от `setup` функцию очистки или ничего. Асинхронный код
выносят во внутреннюю функцию:

```tsx
useEffect(() => {
  const controller = new AbortController()

  const load = async () => {
    try {
      const value = await fetchLastVoltage(controller.signal)
      setVoltage(value)
    } catch (e) {
      if (!isAbortError(e)) setError(errorMessage(e))
    }
  }

  load()
  return () => controller.abort() // ответ на устаревший запрос будет проигнорирован
}, [])
```

`AbortController` решает проблему **гонки запросов**: если эффект перезапустился,
пока старый запрос не завершился, ответ на старый запрос не перезапишет более
свежие данные.

## Когда эффект НЕ нужен

Эффект — «запасной выход» из React. Частые лишние применения:

| Задача | Плохо: через эффект | Хорошо |
|--------|---------------------|--------|
| Значение, вычисляемое из состояния | `useEffect(() => setMean(avg(history)), [history])` | `const mean = avg(history)` при рендере (дорогое — `useMemo`, урок 4) |
| Реакция на действие пользователя | `useEffect(() => { if (clicked) send() }, [clicked])` | вызвать `send()` прямо в `onClick` |
| Сброс состояния при смене пропса | эффект, вызывающий `setX(initial)` | атрибут `key` у компонента |

Признак лишнего эффекта: он только вызывает сеттер на основе другого состояния или
пропсов, не обращаясь к внешнему миру.

## Типичные ошибки

| Ошибка | Последствие |
|--------|-------------|
| Нет массива зависимостей, а в эффекте безусловный `setState` | бесконечный цикл «рендер → эффект → setState → рендер» |
| В зависимостях не указано значение, которое использует эффект | эффект работает с устаревшим значением (stale closure) |
| В зависимостях объект или функция, созданные при рендере | эффект перезапускается после каждого рендера (решение — урок 5) |
| Нет cleanup у таймера или подписки | утечки, дублирование таймеров |
| `useEffect(async () => ...)` | ошибка типов и сломанная очистка |

## `useLayoutEffect` (для справки)

Работает так же, как `useEffect`, но выполняется **до** отрисовки браузером,
синхронно после изменения DOM. Нужен редко: когда нужно измерить размер элемента и
сразу изменить вёрстку без мерцания. Во всех остальных случаях используйте
`useEffect`.

## Вопросы для самопроверки

1. В какой момент выполняется эффект: до или после обновления DOM?
2. Что произойдёт при смене периода опроса, если убрать `return () => clearInterval(id)`?
3. Почему в журнале при открытии страницы эффект A выполнился дважды? Будет ли так в
   собранной версии?
4. Почему эффект B не запускается, если устройство вернуло то же самое значение?
5. Почему `controller` объявлен внутри эффекта D, а не в теле компонента?
